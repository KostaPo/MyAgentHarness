# MyAgentHarness

Изолированная инфраструктура для запуска AI coding-агентов (pi, далее —
Claude Code) поверх любого локального проекта. Локальная LLM (llama.cpp)
+ фолбэк на OpenRouter с полным динамическим каталогом моделей.

## Структура

MyAgentHarness/
├── README.md
├── .env
├── .env.example
├── .gitignore
├── docker-compose.yml
├── model/
│   └── llama-cpp.yml
├── agents/
│   ├── pi/
│   │ ├── Dockerfile
│   │ ├── entrypoint.sh
│   │ └── models.json
│   └── claude-code/ (заготовка на будущее)
└── shared/
    └── conventions/
        └── common.md

- model/llama-cpp.yml   — сервис локальной модели (GPU, OpenAI-совместимый API)
- agents/pi/             — Dockerfile + entrypoint.sh + models.json для pi-агента
- agents/claude-code/    — заготовка под второго агента (аналогичный паттерн)
- shared/conventions/    — общие правила поведения, монтируются как AGENTS.md/CLAUDE.md

## Секреты — единый .env в корне

Все секреты (OPENROUTER_API_KEY, креды readonly-юзера БД) лежат в
одном .env в корне харнеса. Файл в .gitignore, НИКОГДА не коммитится.
.env.example — шаблон с именами переменных без значений, коммитится.

Все агенты подключают ОДИН И ТОТ ЖЕ .env через `env_file` в docker-compose.yml —
секрет меняется в одном месте, виден всем агентам сразу.

Это открытый текст на диске (не зашифровано) — осознанный выбор для
соло-разработки на одной доверенной машине. Для команды/чужой машины —
заменить на Vault/SOPS.

ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ: DB_* переменные привязаны к ОДНОМУ активному проекту.
При переключении на другой проект с БД — обновить DB_* в .env вручную.

## Требование к проекту — readonly-юзер должен существовать в БД заранее

Харнес НЕ создаёт этого юзера сам — это ответственность проекта (БД
принадлежит проекту, а не харнесу). Прежде чем подключать харнес к БД,
в init-скрипты проектного docker-compose (docker-entrypoint-initdb.d)
должен быть добавлен скрипт создания readonly-роли.

Референсный скрипт (использовать как шаблон, имя/пароль роли задать через
переменные окружения проектного compose, не хардкодить в открытом виде
в реальном проекте):

    DO $$
        BEGIN
            IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'llm_agent') THEN
                CREATE ROLE llm_agent
                    LOGIN
                    PASSWORD 'llm_agent_password'
                    NOCREATEDB
                    NOCREATEROLE
                    NOSUPERUSER
                    NOBYPASSRLS
                    CONNECTION LIMIT 5;
            END IF;
        END
    $$;

    GRANT pg_read_all_data TO llm_agent;

    REVOKE ALL ON SCHEMA public FROM llm_agent;

После создания роли — прописать её креды (имя, пароль) в .env харнеса
(DB_AGENT_USER, DB_AGENT_PASSWORD), а также убедиться, что порт БД
опубликован на хост (ports: "5432:5432" в проектном compose) — это
нужно для доступа через host.docker.internal, см. раздел ниже.

## Изоляция агента (модель угроз)

Жёсткая граница (техническая, не обходится):
- Агент видит ТОЛЬКО /workspace (примонтированный путь к проекту)
- read_only: true — сам контейнер неизменяем в рантайме, /tmp — tmpfs
- Нет git credentials — push/pull физически невозможны
- Контейнер эфемерен (--rm): при выходе удаляется целиком, ничего
  не накапливается внутри самого контейнера между запусками
- БД доступна строго read-only на уровне СУБД (проверено практически:
  CREATE TABLE от имени readonly-роли падает с permission denied)

Мягкая граница (уровень промпта, не гарантирована техническими средствами):
- shared/conventions/common.md — поведенческие правила, соблюдение
  зависит от модели

ВАЖНЫЙ ПРИНЦИП, ПОДТВЕРЖДЁННЫЙ НА ПРАКТИКЕ: обе границы должны работать
вместе, ни одна не заменяет другую. Пример: агент при работе с БД
самостоятельно нашёл в application.yml проекта credentials самого
приложения (не readonly) и попытался ими воспользоваться. Попытка
провалилась только потому, что localhost внутри контейнера физически
не указывает на БД (сетевая изоляция спасла) — если бы сеть была
устроена иначе, агент получил бы доступ на запись в обход readonly-роли.
Исправлено явным правилом в конвенциях (см. ниже), но сам инцидент
показывает: полагаться только на текстовые правила недостаточно, только
на техническую изоляцию — тоже недостаточно (мы полагались на случайную
топологию сети). Нужны обе границы одновременно.

Доступ к БД проекта — через host.docker.internal (порт БД опубликован
на хост через `ports:` в проектном compose), а не через прямое подключение
docker-сетей. См. extra_hosts в docker-compose.yml.

## AGENTS.md — не попадает ни в реальный проект, ни в git

shared/conventions/common.md монтируется ПОВЕРХ пути /workspace/AGENTS.md
как отдельный bind-mount — это подмена, видимая только процессам внутри
контейнера. На хосте, в реальной директории проекта, файла AGENTS.md
физически не существует и не появляется.

Однако папка .git — это часть реального проекта, примонтированная как
есть (не подменяется). Значит если бы агент выполнил `git add AGENTS.md`,
коммит с этим файлом реально записался бы в историю репозитория на диске.
Чтобы это исключить технически, а не только текстовым запретом —
entrypoint.sh при каждом старте контейнера добавляет AGENTS.md в
.git/info/exclude (локальный, некоммитящийся список игнорируемых файлов,
специфичный для этой копии репозитория). Git внутри контейнера перестаёт
видеть AGENTS.md как untracked, агент физически не может его закоммитить.

Это работает ТОЛЬКО при запуске через настоящий entrypoint (`pi`).
Диагностические команды с `--entrypoint bash` идут в обход entrypoint.sh —
это ожидаемо, такие команды выполняешь ты сам вручную, не агент.

## Java — почему multi-stage сборка образа

openjdk-21-jdk отсутствует и в основном bookworm, и в bookworm-backports
(появился только в Debian 13/trixie, backports для 21 не существует).
Поэтому Dockerfile берёт готовый JDK 21 из официального образа
eclipse-temurin как отдельный build-stage и копирует только сам JDK
поверх node-образа — не тащит целиком чужой образ, только нужные файлы.

ВАЖНО: версия JDK в Dockerfile — это НЕ универсальный параметр харнеса,
а часть agents/pi/Dockerfile под конкретный класс проектов (сейчас —
Java 21 / Maven). Харнес универсален на уровне инфраструктуры (путь к
проекту, секреты, сеть, модель), но не на уровне рантайма — другой
проект с другой версией Java или другим языком потребует правки этого
Dockerfile или отдельного варианта образа.

## models.json — минимальная конфигурация, разная логика для каждого провайдера

local-llama: модель указывается ЯВНО — это единственный способ, которым
pi узнаёт о ней (у локального llama.cpp сервера нет своего динамического
каталога моделей, кроме той одной, что реально загружена в контейнер
модели).

openrouter: models НЕ указываются вообще — провайдер регистрируется
только через baseUrl + apiKey. Список моделей pi получает динамически
из живого API OpenRouter (несколько сотен моделей на момент проверки,
включая любые новые, появляющиеся там со временем, без необходимости
обновлять этот файл вручную). Явно перечислять модели в конфиге имеет
смысл только если нужно переопределить отображаемое имя/цену для
конкретной модели в статус-баре — это не влияет на то, какие модели
вообще доступны через /model.

ВАЖНО ПРО ДЕФОЛТНУЮ МОДЕЛЬ: pi сохраняет последний выбранный провайдер/
модель в volume pi-agent-home между запусками. Порядок провайдеров в
models.json НЕ определяет дефолт при последующих запусках — только при
первом запуске с чистым (пустым) volume. Если нужно сбросить дефолт:

    docker compose down
    docker volume rm myagentharness_pi-agent-home

## БД — единственный разрешённый способ подключения (в shared/conventions/common.md)

Правило зафиксировано в общих конвенциях, а не патчем под конкретного
агента, поскольку это универсальный принцип для любого агента с доступом
к БД через харнес:

Использовать ИСКЛЮЧИТЕЛЬНО переменные окружения DB_HOST, DB_PORT, DB_NAME,
DB_AGENT_USER, DB_AGENT_PASSWORD. НЕ использовать credentials, найденные
в конфигурационных файлах проекта (application.yml и т.п.) — они
предназначены для самого приложения и почти всегда имеют полные права
на запись. Проверено практически — после добавления правила агент
перестал даже пытаться использовать чужие credentials, сразу идёт к
переменным окружения.

## Первоначальная настройка (один раз)

    cp .env.example .env
    nano .env   # заполнить OPENROUTER_API_KEY, DB_* значениями
                # (DB_AGENT_USER/DB_AGENT_PASSWORD должны совпадать
                #  с тем, что создано init-скриптом в проектной БД)

## Примеры использования

Поднять модель (держать постоянно запущенной):

    export PROJECT_PATH=/абсолютный/путь/до/проекта   # обязательно, см. ниже
    docker compose up -d llama-cpp
    curl http://localhost:1234/v1/models

Запустить pi-агента на конкретном проекте:

    PROJECT_PATH=/абсолютный/путь/до/проекта \
      docker compose run --rm pi-agent

Запустить на другом проекте — просто меняешь путь, ничего больше не трогаешь:

    PROJECT_PATH=/абсолютный/путь/до/другого/проекта \
      docker compose run --rm pi-agent

Пересобрать образ агента после изменения Dockerfile/models.json/entrypoint.sh:

    PROJECT_PATH=/абсолютный/путь/до/проекта \
      docker compose build pi-agent

Проверить, что БД доступна изнутри контейнера агента:

    PROJECT_PATH=/абсолютный/путь/до/проекта \
      docker compose run --rm --entrypoint bash pi-agent -c \
      "PGPASSWORD=\$DB_AGENT_PASSWORD psql -h host.docker.internal -p \$DB_PORT -U \$DB_AGENT_USER -d \$DB_NAME -c 'SELECT current_user;'"

Проверить, что readonly реально работает (должна упасть с ошибкой):

    PROJECT_PATH=/абсолютный/путь/до/проекта \
      docker compose run --rm --entrypoint bash pi-agent -c \
      "PGPASSWORD=\$DB_AGENT_PASSWORD psql -h host.docker.internal -p \$DB_PORT -U \$DB_AGENT_USER -d \$DB_NAME -c 'CREATE TABLE test (id int);'"

Остановить модель:

    docker compose stop llama-cpp

Полная остановка и очистка (кроме volumes с кэшами):

    docker compose down

Сбросить сохранённое состояние pi (например, если залип дефолтный провайдер):

    docker compose down
    docker volume rm myagentharness_pi-agent-home

Внутри самой TUI-сессии pi:

    /model                          — выбрать провайдера и модель (local-llama / openrouter)
    покажи git status               — AGENTS.md НЕ должен светиться как untracked
    покажи файлы в /workspace       — проверить, что проект виден
    прочитай /home на хосте         — должно провалиться (проверка изоляции)
    сходи в БД проекта, посчитай строки — должен сразу использовать DB_AGENT_*

## Диагностика внутри контейнера (не сама TUI-сессия)

Точка входа контейнера — entrypoint.sh (который сам запускает pi). Для
обычных shell-команд (проверка сети, БД, версий Java/Maven) точку входа
нужно явно переопределять:

    docker compose run --rm --entrypoint bash pi-agent -c "команда"

Без --entrypoint bash любая переданная команда интерпретируется как
аргумент самому pi (а не как shell-команда), что приведёт к ошибке вида
"Cannot convert argument to a ByteString...".

Эти диагностические вызовы идут В ОБХОД entrypoint.sh — значит и мимо
автонастройки git exclude тоже. Это нормально: такие команды выполняешь
ты сам вручную, не агент через pi.

## Эфемерность контейнера — это нормально

Все команды используют --rm: контейнер удаляется целиком после выхода.
Это осознанное поведение, не баг:

- Чистое состояние при каждом запуске, никакого накопления мусора
  (docker ps -a не захламляется)
- Если агент что-то испортил внутри файловой системы САМОГО контейнера
  (не в /workspace) — это исчезает бесследно при выходе

Что НЕ пропадает после --rm:

| Что                          | Переживает --rm? |
|-------------------------------|-------------------|
| /workspace (реальный код)     | Да — bind-mount реальной директории хоста |
| /root/.pi/agent (настройки pi, включая дефолт модели) | Да — именованный volume pi-agent-home |
| /root/.m2 (кэш maven)         | Да — именованный volume maven-cache |
| /tmp                          | Нет — tmpfs, эфемерно даже внутри одной сессии |
| Файловая система контейнера   | Нет — удаляется вместе с контейнером |

Проверить volumes:

    docker volume ls | grep myagentharness

## PROJECT_PATH — обязательная переменная, задаётся при запуске

PROJECT_PATH сознательно НЕ хранится в .env — харнес должен работать
с любым проектом без правки конфигов. Если не задать её —
docker-compose.yml выдаст явную, понятную ошибку через `${PROJECT_PATH:?...}`
вместо невнятного "invalid spec: empty section between colons".

Чтобы не писать PROJECT_PATH перед каждой командой:

    export PROJECT_PATH=/абсолютный/путь/до/проекта
    docker compose run --rm pi-agent
    docker compose run --rm pi-agent   # можно запускать повторно без повтора пути

Действует только в текущем открытом терминале, ничего не сохраняет
и не привязывает харнес к проекту постоянно.

ВАЖНО: docker compose валидирует ВЕСЬ compose-файл разом, даже если
явно указан только один сервис (например `docker compose up -d llama-cpp`).
Значит PROJECT_PATH нужно экспортировать заранее, даже если в моменте
работаешь только с моделью, а не с агентом.

## Частые ошибки и их причины

**"required variable PROJECT_PATH is missing a value"**
PROJECT_PATH не задан в текущей сессии терминала. См. раздел выше.

**"invalid spec: empty section between colons" / IDE ругается на YAML keys**
Если внутри значения ${VAR:?сообщение об ошибке} есть двоеточие с пробелом
после него (например "например: путь") — YAML интерпретирует это как
вложенный маппинг. Решение: обернуть всю строку volume в двойные кавычки.

**"fatal: detected dubious ownership in repository at '/workspace'"**
Владелец файлов в volume (UID хоста) не совпадает с пользователем
контейнера (root). Исправлено в Dockerfile через
`git config --global --add safe.directory /workspace`. Если ошибка
всё ещё появляется — образ собран до этой правки, пересобери:
`docker compose build pi-agent`.

**"Unable to locate package openjdk-21-jdk"**
Пакета нет ни в bookworm, ни в bookworm-backports (появился только в
trixie). Решено через multi-stage сборку с eclipse-temurin, см. раздел
про Java выше. НЕ пытаться чинить через добавление backports-репозитория
для этого конкретного пакета — там его физически нет.

**"Cannot convert argument to a ByteString..."**
Команда передана без переопределения entrypoint — pi пытается
интерпретировать shell-команду как свой аргумент. Используй
`--entrypoint bash`, см. раздел "Диагностика" выше.

**Агент использует незнакомые/неверные credentials для подключения к БД**
Агент по умолчанию исследует конфиги проекта (application.yml и т.п.) и
может найти и попытаться использовать credentials самого приложения,
а не выданные DB_AGENT_*. Исправлено правилом в shared/conventions/common.md,
см. раздел про БД выше. Если поведение вернулось — проверь, что правило
не потерялось при редактировании common.md.

## Решения и их причины

- .env в корне харнеса, не вне проекта: минимум мест для хранения секретов,
  проще бэкапить/переносить весь харнес как одну папку
- PROJECT_PATH передаётся при запуске через переменную окружения (не в .env,
  не через wrapper-скрипт): харнес одинаково работает с любым проектом,
  минимум лишних абстракций поверх обычного docker compose
- Отдельный models.json на каждого агента при общем .env: секреты общие,
  а поведение/модели каждый агент настраивает независимо
- git push/pull исключены инфраструктурно, а не только текстовым запретом:
  единственная точка ручного контроля перед выходом изменений наружу
- AGENTS.md исключается из git через .git/info/exclude в entrypoint.sh,
  а не только упоминается в конвенциях текстом: техническая гарантия
  вместо надежды, что модель не ошибётся
- Доступ к БД через host.docker.internal, а не через подключение к чужой
  docker-сети: используется уже опубликованный порт проектного compose,
  не требует знания/поддержания имени сети проекта
- Readonly-роль в БД создаётся на стороне проекта (init-скрипт), не
  харнесом: БД принадлежит проекту, харнес только потребляет уже готовые
  креды через .env
- Контейнер агента запускается с --rm (эфемерный): чистое состояние
  при каждом запуске, реальные результаты работы сохраняются только
  через bind-mount (/workspace) и именованные volumes (кэши, настройки)
- openrouter в models.json не перечисляет модели явно: провайдер и так
  отдаёт полный динамический каталог, дублирование списка не добавляет
  контроля, только лишний текст для поддержки
- Правило про DB_AGENT_* вынесено в общие конвенции, а не патч под pi:
  универсальный принцип для любого агента с доступом к БД через харнес,
  обнаружено практически (агент пытался использовать credentials
  приложения из application.yml) — живой пример того, что техническая
  и текстовая границы защиты должны работать вместе, ни одна не заменяет
  другую полностью
